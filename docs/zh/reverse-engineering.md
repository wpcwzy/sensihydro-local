# 逆向全过程

> 目标设备：艾默生/谷轮 **心海悦 (Sensi Hydro)** 热泵地暖中央空调，6 台内机 + 1 台外机，
> DTU 型号 **HF5111B**（汉枫/High-Flying），固件 1.34.11e。厂商 App 通过
> `sensihydro.copeland.cn` 控制，App 服务商已停止维护，因此需要自建控制通道。

## 0. 结论先行

整条链路其实非常"标准"：

```
App ──HTTPS──▶ 厂商云 ──TCP:5000──▶ DTU(HF5111B) ──RS485 Modbus RTU 19200 8E1──▶ 主控板 ──▶ 6 台内机
```

DTU 是一个**只会往外连**的透明串口网关：它把「TCP 连接上的字节」和「RS485 上的 Modbus RTU 帧」
互相转换。厂商云在 5000 端口上说的就是**标准 Modbus TCP（MBAP 帧）**，
所以只要我们能接住 DTU 的连接，就能直接读写主控板寄存器。

## 1. 定位 DTU 与它的"性格"

1. 在路由器/交换机上看 ARP 表，找到空调网关的 MAC（`34:EA:E7:xx:xx:xx` 前缀是汉枫模块），
   得到 IP（示例中为 `192.168.1.20`）。
2. 端口扫描：

   | 端口 | 协议 | 用途 |
   |---|---|---|
   | 23 | TCP | Telnet 配置台（部分固件开放） |
   | 48899 | UDP | 汉枫 IOTService 工具发现/配置协议 |
   | 80 | TCP | 内置网页配置（部分固件开放） |

3. 用 IOTService 协议（UDP 48899 广播 JSON 公告，DTU 会反向连回 48907 端口）
   可以读/写 DTU 配置、执行 `reload`。本仓库 `tools/dtu_reload.py` 就是这一步的复刻。
   关键信息：

   - 工作模式：`TCP Client`
   - 目标服务器：`sensihydro.copeland.cn:5000`
   - 串口：`19200, 8, E, 1`（偶校验）
   - 心跳：连接建立后周期性发送 `00` + 12 位 MAC 的 ASCII 字符串

> 这一步只读取，不修改任何配置——**DTU 配置保持原样**是能"官方 App 与本地控制并存"的前提。

## 2. 反编译 OEM App，拿到云端 API

用 jadx 反编译 App（`com.emerson.sensihydro.*`）：

- API Base：`https://sensihydro.copeland.cn/api/v2`；
- 登录：`POST /login`（手机号 + 密码），返回 JWT，之后放在 `x-access-token` 头里；
- 设备列表：`GET /device/list`，内机列表：`GET /unit/list/{deviceId}`；
- 所有控制都走 `POST /unit/update`，用 `modifyVal` 区分：`1` 开关、`2` 模式、`3` 睡眠、
  `4` 温度（`flag` 区分 ±0.5）、`5` 风速；
- 主机模式（常规/节能/静音/强热）走 `POST /device/updateMode`，值是 `deviceMode` 0~8；
- 外机/内机参数表：`GET /customservice/selectConfigById/{serialno}`（**很慢**，实测 15 秒左右）。

这些接口没有文档、也没有稳定性承诺，仓库里 `custom_components/sensihydro/api.py`
是它们的"客户端实现"，云端变化时这里需要维护。

## 3. 用 DNS 重定向接住 DTU

DTU 只会连 `sensihydro.copeland.cn:5000`。在局域网 DNS 上把这个域名解析到 bridge 所在机器，
DTU 就会连到我们。但**直接把厂商域名全局改到内网会坏事**：

- 官方 App / Home Assistant 也用同一个域名走 **HTTPS(443)**；
- 443 上没有服务 → 云端接口全部超时，HA 集成直接崩。

所以最终方案是**分流 DNS**：只把 DTU 这一台设备的解析结果改掉
（AdGuard「按客户端上游 DNS」→ bridge 内置 DNS `:15353`），其它设备照常解析公网。
详见 [architecture.md](architecture.md)。

## 4. 中继 + 抓包：确认 5000 端口就是 Modbus TCP

bridge 的 `:5000` 同时做两件事：

1. 把 DTU 发来的帧**原样转发**给真正的厂商服务器（`40.73.97.71:5000`），
   把厂商回包原样转回 DTU —— 官方 App 完全无感；
2. 在转发过程中**旁路解析**帧结构：
   `[事务号 2][协议号 0x0000 2][长度 2][单元号 1][功能码 1][数据…]`，
   这就是标准 Modbus TCP（MBAP）。功能码主要是 `0x03`（读保持寄存器）、
   `0x06`（写单个）、`0x10`（写多个）。

观察云端轮询到的寄存器地址后，就能猜出内机状态/控制块的位置（见
[registers.md](registers.md)）。

## 5. 试探寄存器（只读 → 小步写 → 双向验证）

1. **只读扫描**：以 20 个寄存器为一块读 `0x00C8` 起的区域，能读到"看起来像温度"的值
   （例如 4800、1780），发现温度编码是 `raw = 3000 + ℃ × 100`；
2. **定位内机槽位**：状态块每 20 个寄存器一个槽位（`0x00C8 + 20n`），
   控制块每 15 个寄存器一个（`0x03E8 + 15n`），共 7 个槽位（其中 1 个空）；
3. **写入验证**：先写目标温度 ±0.5℃，用「读回寄存器」+「官方 App 显示」+
   「线控器/机器实际反应」三方交叉验证，确认控制块偏移：
   `+0` 开关、`+1` 模式<<8|开关位、`+2` 目标温度、`+3` 风速；
4. **注意限制**：控制器单次读最多 20 个寄存器（读更多会超时/异常回包），
   写入后需要几百毫秒才生效，连续写太快会被丢弃。

## 6. 主机模式（常规/节能/静音/强热）的破解

App 里切换"主机模式"时，抓 bridge 日志能看到一串 **写寄存器** 的突发流量，
地址固定在 `0x05DD`、`0x05DE`、`0x05E0`：

- `0x05DD`：出水温度设定（45℃ 常规/节能/静音，50℃ 强热）；
- `0x05DE`：静音标志（1 开 / 2 关）；
- `0x05E0`：节能标志（1 开 / 2 关）。

三个开关位（静音、节能、强热）组合出 8 种模式，正好对应云端 `deviceMode` 0~8。
关键坑：

- **写顺序**：先写两个标志，最后写 `0x05DD`；
- **间隔**：控制器要求相邻两条写命令间隔约 2–5 秒（云端自身实测间隔 4–5 秒），
  太密会被静默丢弃 → 实现里做了「写 → 回读校验 → 重试」。

## 7. 验证与收敛

最终以三方一致为准：

1. 本地寄存器读回的值；
2. 官方 App 里显示的状态（云端有 15–30 秒延迟，属正常）；
3. 机器/线控器的实际反应。

本仓库的 HA 集成就是这样做的：局域网直读直写，云端只做兜底和补充
（故障标志、外机参数表里本地读不到的文字状态）。

## 8. 踩过的坑（供参考）

| 坑 | 现象 | 处理 |
|---|---|---|
| 全局 DNS 重定向 | HA 云端接口超时、App 在家连不上 | 改用按客户端分流 DNS |
| 把 DNS 指向内网但 443 无服务 | HTTPS 握手失败 | 同上 |
| 单次读超过 20 个寄存器 | 超时/无响应 | 分块读 |
| 切模式后立刻写目标温度 | 温度写丢 | 等待 2 秒 + 重试 |
| 每次请求都现读 12 个寄存器 | 网页点一下要 2–3 秒 | 后台快照 + 乐观更新 |
| 云端 `selectConfigById` 慢（15s+） | HA 集成整体 unavailable | 把"扩展数据"失败改为非致命 |
| DTU 一直连着旧地址 | 切换 DNS 后不生效 | 用 JCMD `reload` 断开重连（或空调断电重启） |
