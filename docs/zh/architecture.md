## 总览

## 为什么不能"全局"重定向 DNS

DTU 只会连厂商域名，所以必须让这个域名对 **DTU** 解析到 bridge。但同一套 DNS
也服务手机 App 和 Home Assistant，它们用同一个域名走 **HTTPS 443** 访问云端 API。
如果把域名全局改到 NAS：

- `NAS:443` 没有服务 → App / HA 的云端请求超时；
- HA 集成会因为云端接口持续失败进入 `setup_retry`，所有实体 `unavailable`；
- 严重时官方 App 在家里完全不可用。

**正确做法：分流 DNS。** 只有 DTU 一台设备的解析结果被改：

```
DTU (192.168.1.20) ──查询──▶ AdGuard ──(按客户端上游)──▶ bridge:15353 ──▶ 192.168.1.10
其它设备            ──查询──▶ AdGuard ──(默认上游)─────▶ 公网 DNS ──▶ 厂商真实 IP
```

- bridge 内置一个迷你 DNS（`bridge/dnsd.py`，UDP+TCP 15353 端口）：
  只对 `sensihydro.copeland.cn` / `sensihydro.insinkerator.com.cn` 返回 bridge IP，
  其它查询转发给 `223.5.5.5 / 119.29.29.29`；
- AdGuard Home 里给 DTU 建"客户端"，给它单独指定上游 `bridge-ip:15353`；
- 全局 `$dnsrewrite` 规则必须删掉。

`tools/switchover.py` 就是通过 AdGuard API 完成上述配置（并清理旧规则）的脚本。

## relay 的工作方式

`bridge/relay.py`：

1. 在 5000 端口 `accept` 到 DTU 的连接后，立即向真实厂商服务器建一条新连接；
2. 两个方向都有数据就用 `selectors` 非阻塞转发；
3. 需要读/写寄存器时，bridge 自己构造 Modbus TCP 帧发往 DTU 方向，
   事务号使用 `0x8000`–`0x8FFF` 段，与云端请求区分；
4. 从 DTU 回来的响应如果是我们的事务号，就交给等待中的请求，**不透传给云端**；
   否则原样透传；
5. 所有注入请求串行化（一把锁），避免 RS485 上出现交错的请求。

由于厂商云仍然收到完整的 DTU 流量，官方 App 看到的设备状态、在线状态都正常。

## 请求/响应模型

`bridge/relay.py` 提供同步的 `read_registers()` / `write_register()`：
构造帧 → 提交给写队列 → 等待对应事务号的响应（带超时）→ 返回/抛异常。
HTTP API、状态后台线程、HA 集成都基于这两个原语。

## 状态快照（性能）

一次全量读取 = 6 台内机 × 2 次读 = 12 次 Modbus 往返 ≈ 2.4 秒。
如果每次 HTTP 请求都现读，网页点一下温度就要 2–3 秒。因此
`bridge/state.py` 维护一个后台快照：

- 有人使用 API 时每 3.5 秒刷新一次；空闲 45 秒后停止（不长期占用 RS485 总线）；
- `/api/state` 直接从内存返回（毫秒级）；
- 写操作不回读，写完立刻返回，后台刷新会在一两秒内补上真实状态。

## cloud 与 LAN 的关系

| 路径 | 作用 |
|---|---|
| 云端（HTTPS API） | 官方 App 的数据源；HA 集成的兜底控制路径；故障/保护标志、部分文字状态 |
| 局域网（Modbus） | 实时状态、控制命令的首选路径；外机诊断参数；主机模式 |

HA 集成每轮轮询会：
1. 拉云端内机列表；
2. 拉 bridge 的 `/api/state`，按**内机名字**匹配后覆盖状态（开关/模式/温度/风速/室温）；
3. 用 bridge 读到的值覆盖参数表里能本地读到的项；
4. 写命令优先走 bridge，失败自动回退云端。

> 匹配依赖"内机名字"：bridge 里的单元名必须与官方 App 里的房间名一致。

## 诊断实体与历史记录

云端参数表（`customservice/selectConfigById`）里的字段分两类：

1. **故障/保护标志**（`val125_*`…`val131_*`、`val211_*`、`val212_*`，约 131 个）：
   聚合成**一个** `故障汇总` 传感器——全部正常时状态是 `正常`，否则按“房间 故障名”列出
   全部活动故障，多个用逗号分隔；每个标志的原始值放在 `flags` 属性里。
   此前它们是上百个独立传感器，云端偶尔把值返回成 `null` 时这些实体就会闪成“未知”。
2. **参数类**（温度/压力/转速/版本/识别码…）：**保持独立传感器**，不聚合。

为了让历史曲线连续（不再被“未知”切碎）：

- 参数表**合并更新**：云端偶尔只返回部分字段时，不再覆盖掉已有数据；
- 传感器值**粘滞**：某一轮拿不到值时沿用上一次的值，而不是变 `unknown`；
- 重启后通过 `RestoreEntity` 恢复上一次的状态，重启瞬间也不产生断点。


## 诊断数据：本地优先（v1.2.0）

**曾经的故障**：95+ 个诊断实体（外机 25 项运行参数 + 6 台内机各 12 项参数）都是从
厂商云的运行参数表 `customservice/selectConfigById` 创建的。这个接口很慢（10~40 秒）、
偶发返回 `--`，HA 重启时只要它失败一次，这些实体就不会被创建，界面上全部变成**不可用**
（registry 里成了"恢复态"），必须手动重载集成才回来。

**现在的做法**：参数表是固定的，因此

1. `params.py` 里静态定义了全部参数（名称与云端完全一致），**实体永远会被创建**；
2. 数值优先从控制器本地读取：
   - 外机 `val100..val124` → 保持寄存器 `0x0064..0x007C`（温度/压力/电流/压缩机频率/
     继电器状态/运行模式/除霜等 25 项全部可解码）；
   - 内机 `val200..val213` → 各内机状态块 `0x00C8 + 20×(槽位-1)`（版本、识别码、回风温度、
     浮球开关、地暖阀、排水泵、二通阀、风机转速、线控器温度）；
3. 只有**故障/保护标志**（`val125_*`、`val211_*`…）没有已知寄存器，仍取云端；
4. 云端参数表改为**后台刷新**（不阻塞 HA 启动），失败后 90 秒重试，超时放宽到 75 秒；
5. 云端整体不可达时，用**缓存的内机列表**继续工作（本地控制不受影响），不再让整个集成
   变成不可用。

每个参数实体都有 `value_source` 属性（`local` / `cloud`），一眼能看出数据来源。
自测：`python3 tests/test_param_decoding.py`。

## 云端状态对账（LAN → 云）

厂商云的状态只在**云端自己下发命令**时更新：通过 bridge 直接写 Modbus 寄存器，云端是不知道的，
于是官方 App 会显示旧状态（"HA 里开了，App 里还是关的"）。

HA 集成因此每轮轮询做一次对账：把本地寄存器的状态和云端记录比较，
不一致且**持续 3 分钟**（避免和 App 刚发出的、还在路上的命令打架）时，
通过云端 API 把本地状态补发上去，同一台内机 5 分钟内最多补一次：

| 项目 | 处理 |
|---|---|
| 开关 | 云端 status 与本地不符 → 云端 `modifyVal=1` 开机/关机 |
| 模式 | 开机状态下不符 → 云端 `modifyVal=2` |
| 目标温度 | 开机状态下不符 → 云端 `modifyVal=4`（flag+base 方式精确设定，关机时云端会拒绝） |

每轮每台内机只补一项，逐项收敛；对账结果会记录在集成日志里（`mirrored ...`）。

## 链路健壮性（看门狗与容错）

设备链路是「DTU ⇄ bridge ⇄ 厂商云」的透传，任何一端静默都可能留下"连接还在但数据不动"的假死状态，因此 bridge 做了这些保护：

| 机制 | 说明 |
|---|---|
| **云端静默看门狗** | 厂商云 300 秒内一个字节都没发（连接还在）→ 主动断开，让 DTU 重连并向云端重新注册 |
| **DTU 静默看门狗** | DTU 180 秒没有任何数据（含心跳）→ 主动断开、等待重连 |
| **字节流校验** | 先校验 MBAP 头（协议号 0、长度合法）再当帧处理；脏字节丢弃并计数，绝不转发给云端（会把云端会话搞乱） |
| **心跳识别** | `00` + 12 位十六进制（可带 CRLF）识别为 DTU 心跳并原样转发；TID 形如 `0x00xx` 的合法 Modbus 帧不会被误判为心跳 |
| **迟到响应吞掉** | 注入请求超时后 DTU 迟到的响应会被丢弃，不再作为"云端帧"泄漏给厂商服务器 |
| **注入 TID 校验** | 只有"事务号 + 功能码"都匹配才认为是自己的响应，避免误吞云端响应 |
| **队列上限** | 任一方向积压超过 1 MB 就主动断开重连，避免内存膨胀 |
| **发送失败即重连** | 发送出错直接断开，由看门狗/重连逻辑恢复，不保留半死连接 |

另外降低了总线占用：状态快照只在有人使用时每 5 秒刷新（活跃窗口 8 秒），空闲时完全停止注入，
避免把 RS485 和 DTU 的心跳通道挤占。

> 如果 `/health` 里 `cloud_idle_drops` 持续增长、`cloud_frames` 不动，说明厂商云一直不肯恢复轮询；
> 此时给空调主控板（DTU）断电重启一次，让它重新向云端注册即可。

## 端口一览

| 端口 | 谁监听 | 说明 |
|---|---|---|
| 5000/TCP | bridge | DTU 回连；**必须**用 host 网络或端口映射 |
| 8090/TCP | bridge | 网页遥控器 + JSON API（无鉴权，仅限局域网） |
| 15353/UDP+TCP | bridge | 分流 DNS（只给 DTU 用） |
| 48899/UDP、48907/TCP | 本机脚本 | 汉枫 IOTService 协议，仅切换/排障时临时使用 |

## 部署形态

- **推荐**：NAS Docker，`network_mode: host`；
- 不支持 host 网络时，用 `ports:` 映射 5000/8090（DNS 的 UDP 也需要映射）；
- bridge 可以跑在任何 Linux 主机上（Python 3.11+，无第三方依赖；也可用 Dockerfile）。

## 安全

- 8090 的网页/API **没有鉴权**：只在内网开放，不要把端口映射到公网；
- bridge 不保存厂商账号密码，账号只存在 HA 集成里；
- DTU 配置不被修改，回滚只需删掉 AdGuard 客户端条目并停容器。
